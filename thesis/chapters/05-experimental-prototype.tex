\chapter{Experimental Prototype}
\label{ch:prototype}

\section{Introduction}

The previous chapters described what \projectname{} is meant to do and why the
market has room for it. This chapter describes what was actually built, and then
measures it. It covers the environment and technologies used, the architecture
of the implemented system, the internals of the matching engine --- the part of
the platform that carries the innovation claimed in
Chapter~\ref{ch:innovation} --- the user interfaces, including the paid matching
tier and the administration console, the experimental evaluation of the
prototype on its own data, and the way the system is packaged for deployment.

Every figure reported in this chapter was measured on the running prototype:
on its database, its logs and its containers, or by scripts run against its two
models. Where a number comes from a small or hand-built sample, the sample is
described next to the number, so that the reader can judge how far it
generalises.

Two decisions shape everything that follows and are worth stating up front.
First, \textbf{no model inference ever happens inside an HTTP request}: encoding
a photograph with a vision transformer takes long enough that doing it while the
user waits would make reporting an item feel broken, so all inference is pushed
onto a background worker and the API answers immediately. Second,
\textbf{vectors live in the main database}, not in a separate vector store: the
core query of this platform is \dq{find items of the opposite type, still open,
reported within a plausible date window, whose description or photograph
resembles this one}, and that is one query joining relational predicates to a
similarity search. A dedicated vector index such as FAISS~\cite{johnson2021faiss}
or a managed vector database would be faster in isolation, but it cannot apply
those relational predicates, so the system would have to retrieve loosely and
filter afterwards in application code --- discarding most of what it fetched and
losing transactional consistency between an item and its vector. At the scale
this platform will reach in its first years, that trade is not worth making.

\section{Development environment, tools and technologies}

\subsection{Hardware environment and editors}

Development was carried out on a laptop workstation (Intel Core i7-8850H, six
cores at 2.6\,GHz, 16\,GB of memory) running Windows~11, with the entire stack
executing inside Linux containers through Docker Desktop. Model inference runs
on CPU: both encoders used by the platform are small enough that a GPU is a
convenience rather than a requirement, and building for CPU keeps the deployment
target realistic for the low-cost hosting described in
Chapter~\ref{ch:finance}. All latencies reported in
Section~\ref{sec:evaluation} were measured on this machine. Source editing was
done in Visual Studio Code, with the Python and TypeScript language servers
providing type checking.

\subsection{Collaborative tools and version control}

The project is a single Git repository containing the backend, the frontend, the
deployment kit and the design documentation, so that a change touching an API
contract and its client can be reviewed as one unit. GitHub hosts the remote. The
API documentation is not written by hand: FastAPI derives an OpenAPI schema from
the Pydantic models, and an interactive Swagger interface is served alongside the
running API, which means the contract shown to the frontend developer is
generated from the code that enforces it and cannot drift away from it.

\subsection{Machine-learning stack}
\label{sec:ml-stack}

Two pre-trained encoders are used, both loaded through the
\code{sentence-transformers} library~\cite{sentencetransformers} so that a
single call (\code{.encode()}) covers text and images alike, and both run on
CPU builds of PyTorch.

\paragraph{Text: multilingual MiniLM (384 dimensions).} The model,
published as \code{paraphrase-\allowbreak multilingual-\allowbreak
MiniLM-\allowbreak L12-\allowbreak v2}, is a Sentence-BERT
model~\cite{reimers2019sbert} --- a BERT~\cite{devlin2019bert}
transformer~\cite{vaswani2017attention} fine-tuned so that whole sentences,
rather than individual tokens, occupy a space where cosine distance is
meaningful --- made multilingual by knowledge distillation from an English
teacher onto a multilingual student, so that translations of the same sentence
are mapped to nearby vectors~\cite{reimers2020multilingual}.

The choice of a \emph{multilingual} encoder is forced by the market described in
Chapter~\ref{ch:market}: reports arrive in Arabic, French and English, and
frequently mix two of them. The English-only encoder usually quoted for this
task, \code{all-MiniLM-L6-v2}, was measured against the production model on the
same reports (Section~\ref{sec:eval-crosslingual}). On a French and an English
description of the same black Samsung phone, the English-only model gives a
cosine similarity of $0.276$ --- the level of unrelated sentences --- while the
multilingual model gives $0.817$. The multilingual model also produces 384
dimensions, so it replaced the English one without any change to the database
schema.

\paragraph{Images: CLIP ViT-B/32 (512 dimensions).}
CLIP~\cite{radford2021clip} is a vision transformer~\cite{dosovitskiy2021vit}
trained contrastively on image--caption pairs. Photographs are compared only to
other photographs, so no language is involved on the image side and the standard
checkpoint is the correct choice. CLIP is preferred to the penultimate layer of
a supervised classifier because its representation is general-purpose: it was
never trained on a fixed label set, and lost property is an open-ended category
by definition.

\paragraph{Why not one model for both.} CLIP embeds images and text into a
shared space, which is attractive at first glance. But the dominant comparison
in this system is text against text --- one person's description of a wallet
against another person's description of the same wallet --- and for that a
dedicated sentence encoder is both stronger and cheaper than CLIP's text tower.
CLIP's text encoder remains available for a future cross-modal signal, matching
the \emph{words} of one report against the \emph{photograph} of another.

\subsection{Why inference runs outside the request cycle}

Encoding one photograph with CLIP takes a median of 98\,ms on the development
CPU, and 147\,ms at the 95th percentile (Section~\ref{sec:eval-performance}); the
worker process that holds both models occupies 872\,MB of memory, against
142\,MB for the API. Performing inference inside \code{POST /items} would
therefore impose three costs: the user waits for a neural network before seeing
any confirmation, every API process must hold the model weights, and API latency
becomes coupled to model load time on every cold start.

Separating the worker removes all three. The API validates the report, persists
it, returns \code{201~Created}, and enqueues a job. The item is publicly
browsable immediately with \code{processing\_status~=~pending}, and the worker
advances it through \code{embedding} and \code{matching} to \code{ready},
setting \code{failed} on any unhandled error so that a periodic sweep can retry
it. The business lifecycle of the item (\code{open}, \code{matched},
\code{claimed}, \code{closed}) is deliberately kept in a separate column from
this pipeline state, because they answer different questions: an item can be
perfectly browsable while its matches are still being computed.

\subsection{Implemented data model}

Lost items and found items are stored in \textbf{one \code{items} table
discriminated by a \code{type} enum}, not in two tables. They share every column,
the same embedding pipeline and the same lifecycle; the only difference is the
direction in which matching searches. Two tables would have duplicated the
schema, the indexes and the embedding code, and forced a \code{UNION} into every
browse query.

\subsection{Generating the embeddings}

The worker assembles one document string from the structured and free-text
fields of a report and encodes it in a single pass. Normalising at encode time
makes every vector unit length, so that the cosine similarity between two
vectors equals their dot product and \code{pgvector}'s cosine distance operator
is directly usable without further scaling.

\begin{lstlisting}[language=Python,caption={Building and encoding the text document},label={lst:embed}]
doc = f"{title}. {description}. category: {category_name}. " \
      f"color: {color}. brand: {brand}."

text_embedding = text_model.encode(doc, normalize_embeddings=True)  # 384-d
\end{lstlisting}

Each photograph is embedded independently and stored on its own row, rather than
averaged into a single per-item vector. Averaging would blur a decisive close-up
together with an out-of-focus wide shot; keeping them separate lets the scoring
stage take the \emph{maximum} similarity over the cross product of the two
items' photographs --- best shot against best shot. An item with no photograph
simply has no image vector, a case the fusion step handles explicitly.

Both models are loaded once per worker process and warmed at startup, so their
load cost is paid on deployment rather than on the first report of the day.

\subsection{Retrieving candidates}

The engine never scores the whole table. Retrieval is a funnel with a cheap
relational stage followed by an approximate nearest-neighbour stage.

\paragraph{Stage A --- relational pre-filter.} Candidates must be of the
opposite \code{type}, still \code{open}, and carry a \code{lost\_or\_found\_at}
date inside a plausible window. The window is deliberately wide and symmetric
(30 days by default): a found report can \emph{precede} the corresponding lost
report, because people frequently pick something up before its owner notices
the loss.

\paragraph{Stage B --- approximate nearest-neighbour search.} Over the
pre-filtered set, \code{pgvector}'s cosine operator \code{<=>} retrieves the top
$K$ candidates using the HNSW index.

\begin{lstlisting}[language=SQL,caption={Candidate retrieval, filters and vector search in one query},label={lst:ann}]
SELECT i.id,
       1 - (i.text_embedding <=> :query_vec) AS vector_sim
FROM items i
WHERE i.type   = :opposite_type
  AND i.status = 'open'
  AND i.lost_or_found_at BETWEEN :date_lo AND :date_hi
  AND i.text_embedding IS NOT NULL
ORDER BY i.text_embedding <=> :query_vec    -- uses the HNSW index
LIMIT :k;                                    -- k = 50
\end{lstlisting}

\paragraph{The second route.} A text search alone systematically loses one case:
a good photograph attached to a two-word description. Such an item is never
retrieved by the text query, so it can never be scored, so it can never be
suggested --- however obviously the photographs match. The engine therefore runs
a \emph{second, independent} retrieval over \code{item\_images.image\_embedding},
adds any item found that way to the candidate set, and scores it on both
modalities afterwards. An item can thus surface through strong wording \emph{or}
through a strong photograph, and is then judged on everything available. On the
evaluation corpus a matching pass examined 15.8 candidates on average and
persisted 2.0 of them (Section~\ref{sec:eval-matching}).

\subsection{Calibrating the image similarity}
\label{sec:calibration}

This was the most instructive finding of the implementation, and it is worth
reporting because the naive version fails silently rather than loudly.

CLIP image embeddings are \emph{anisotropic}: they do not spread over the unit
sphere but occupy a comparatively narrow cone. This is a known property of
representations learned by contrastive and self-supervised
objectives~\cite{ethayarajh2019anisotropy}, and in multimodal contrastive models
it is compounded by a separation between the image and text
manifolds~\cite{liang2022modalitygap}. Figure~\ref{fig:clip-hist} shows the
consequence on the platform's own photographs. Across the 712 pairs of
photographs taken from two different reports that were \emph{not} confirmed as
the same object, the raw cosine similarity has a median of $0.578$ and a 90th
percentile of $0.738$; 31.9\,\% of these pairs score $0.65$ or more. The five
pairs whose reports were confirmed by their owners as the same object score
between $0.861$ and $0.949$.

Fed directly into a weighted average with a weight of $0.5$, a raw score of
$0.58$ --- the \emph{typical} unrelated photograph --- contributes $0.29$ to the
combined score, enough to lift weak text matches over the persistence threshold
and put unrelated objects in front of users. The fix is to rescale the interval
$[f, 1]$ onto $[0, 1]$, where $f$ is a configured floor:

\begin{equation}
s_{\text{img}} = \operatorname{clamp}_{[0,1]}\!\left(\frac{s^{\text{raw}}_{\text{img}} - f}{1 - f}\right),
\qquad f = 0.65 .
\label{eq:calibrate}
\end{equation}

Under this mapping the median unrelated pair ($0.578$) becomes $0$, the 90th
percentile ($0.738$) becomes $0.25$, and the confirmed pairs ($0.861$--$0.949$)
become $0.60$--$0.85$. Clamping at zero matters as much as the rescaling: it
means \dq{less alike than an ordinary pair of photographs} reads as \emph{no
evidence} rather than as negative evidence capable of dragging down an otherwise
sound textual match. The floor is not a perfect separator --- about a third of
the unrelated pairs still carry a small positive image score --- which is why
the image channel is never allowed to decide alone: the text score, the metadata
and the thresholds below must agree with it.

\subsection{Fusing the scores}

Two adjustments are applied before fusion.

\paragraph{Lexical blending.} Embeddings capture meaning but blur exact tokens.
\dq{iPhone 14 Pro} and \dq{iPhone 13 Pro} sit almost on top of each other in
vector space, yet that difference is the entire identification. PostgreSQL's
full-text search scores them apart, so the semantic similarity is blended with a
lexical score, weighted towards the vector because exact overlap is precise when
present but absent for most genuine matches --- two people describing one object
in different words is the reason embeddings are in the system at all.

\begin{equation}
s_{\text{text}} = \operatorname{clamp}_{[0,1]}\!\big((1 - w_{\ell})\, s_{\text{vec}} + w_{\ell}\, s_{\text{lex}}\big),
\qquad w_{\ell} = 0.25 .
\label{eq:lexical}
\end{equation}

\paragraph{Weighted fusion with redistribution.} A missing photograph must not be
scored as a \emph{dissimilar} photograph. Renormalising by the weights that
actually fired means an item without a photograph is judged purely on its text,
at full scale, instead of being capped at $w_{\text{text}} = 0.5$ and ranking
below every photographed item however well it matches:

\begin{equation}
s_{\text{comb}} =
\frac{w_{\text{text}}\, s_{\text{text}}\, \mathbf{1}_{\text{text}}
    + w_{\text{img}}\, s_{\text{img}}\, \mathbf{1}_{\text{img}}}
     {w_{\text{text}}\, \mathbf{1}_{\text{text}}
    + w_{\text{img}}\, \mathbf{1}_{\text{img}}} ,
\label{eq:fusion}
\end{equation}

\noindent where $\mathbf{1}_{m}$ is the indicator that modality $m$ is present
for both items of the pair.

\subsection{Computing confidence and explanations}

The combined score measures embedding proximity. \emph{Confidence} is the
user-facing estimate that the pair really is the same object; it starts from the
combined score and adds small bounded rewards for independent corroboration:

\begin{equation}
c = \operatorname{clamp}_{[0,1]}\!\Big(s_{\text{comb}}
  + b_{\text{cat}} + b_{\text{col}} + b_{\text{brand}} + b_{\text{wil}}
  + b_{\text{time}} \cdot \tau + b_{\text{margin}} \cdot \mu \Big).
\label{eq:confidence}
\end{equation}

The boosts are deliberately small (Table~\ref{tab:params}). Together they can
lift a plausible match above the notification threshold, but they can never
manufacture a match out of an unrelated pair --- which is the failure that
matters more. A false \dq{we found your wallet} costs far more trust than a
missed suggestion costs opportunity.

Several details of the implementation follow from that asymmetry:

\begin{itemize}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{Category agreement counts only when both sides declared one.}
        Agreement on \emph{unknown} is not agreement, and 17 of the 56 reports
        in the evaluation corpus carry no category at all.
  \item \textbf{Proximity is measured by wilaya, not by radius.} The report form
        does not ask for coordinates and no report in the corpus carries any, so
        a distance term would have been dead code. Wilayas are stored as
        numeric codes rather than names, so that a location can be rendered in
        Arabic, French or English without touching stored data.
        \emph{Known limitation:} the implementation carries the 58 wilayas in
        force since December 2019, whereas eleven further wilayas were created
        on 16~November 2025, bringing the national total to
        69~\cite{wilayas2025}. Because the new codes extend the sequence rather
        than renumbering it, updating the list is an additive change to one
        module and its client mirror.
  \item \textbf{Temporal plausibility is directional.} An object is found
        \emph{after} it is lost, so the reverse ordering is penalised --- but
        halved rather than zeroed, because people notice a loss late and
        remembered dates are approximate.
  \item \textbf{Distinctiveness is rewarded.} A top candidate standing clearly
        above the runner-up is more trustworthy than the same score in a
        five-way tie, where the similarity is probably measuring \dq{generic
        black wallet} rather than \emph{this} wallet. Because this term depends
        on the rest of the field, it is applied once every candidate has been
        scored.
\end{itemize}

\paragraph{Explanations as reason codes.} The interface shows the confidence as
a percentage together with the reasons that produced it. Those reasons are
emitted by the worker as \textbf{codes with parameters} --- \code{same\_category},
\code{same\_wilaya}, \code{time\_close} with a day count --- and never as
English prose. The worker cannot know which of three languages the eventual
reader uses; the frontend translates the codes through the same message
catalogues that drive the rest of the interface.

or isotonic regression~\cite{zadrozny2002calibration,guo2017calibration} --- and
holding them behind a single scoring interface means the learned version can
replace the hand-set one without touching the API, the database or the
interface.

\subsection{Persistence, retraction and notification}

Three behaviours make the engine safe to re-run, which matters because matching
is triggered again whenever either side of a pair is edited.

\begin{itemize}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{Idempotence.} The \code{matches} table is unique on the (lost,
        found) pair, so a re-run \emph{upserts} updated scores rather than
        accumulating duplicates.
  \item \textbf{Retraction.} Any pair that a pass no longer supports is expired.
        Without this, re-scoring could only ever add suggestions; an item whose
        candidate pool had closed would go on displaying matches it no longer
        has. In the evaluation corpus, 12 of the 43 suggestions ever created
        were later expired this way.
  \item \textbf{Notification on transition only.} A user is notified when a pair
        \emph{crosses} the notification threshold, not on every upsert.
        Re-running the matcher over the whole evaluation corpus produced no
        duplicate notification.
\end{itemize}

The landing page states the proposition in one line, offers the two entry points

\subsection{Registration and authentication}

Registration takes an e-mail, a full name and a password. Passwords are hashed
with Argon2, the memory-hard function standardised in RFC~9106~\cite{argon2rfc}.
Sessions use access tokens valid for 15 minutes paired with rotating refresh
tokens valid for 30 days, and every rotation invalidates its predecessor.

Reuse of an already-rotated refresh token is treated as potential theft and
revokes the session chain --- but only outside a 30-second grace window. That
window exists because the benign case is common: a second browser tab, a page
reload in mid-refresh, or a retried request will legitimately replay the
previous token, and without it a single stale replay would log the user out of
every device they own. Outside development, the API refuses to start if its
signing secret is the development default or shorter than 32 characters.

\subsection{Reporting an item}

One guided form, in five steps, serves both directions, differing only in
wording and in the date label. It collects a title, a free-text description, a
category, colour, brand, wilaya, the date, up to two verification questions, and
up to five photographs.

Uploads are validated on content rather than on file extension --- declared MIME
type, magic bytes and size --- then re-encoded with Pillow to WebP at quality~82
with the longest edge bounded at 1\,600\,px. The 39 photographs stored for the
evaluation corpus occupy 3.2\,MB in total, with a mean of 63\,KB and a median of
30\,KB per file. At that size, the 40\,GB disk of the smallest server considered
in Chapter~\ref{ch:finance} holds several hundred thousand photographs, so
storage is not a cost driver at pilot scale.

\subsection{Browsing and searching}

The public browse views list lost and found reports with filters on category,

with accent folding (\code{unaccent}) and trigram matching for misspellings.
Keyword search is a genuine fallback rather than a lesser version of the
matching engine: a user who knows the brand name written on the object wants
exactly that token, not its neighbourhood in vector space.

\subsection{Item detail and match suggestions}

The detail page shows the report, its photographs, and --- for the owner --- the
ranked suggestions produced by the engine. Each suggestion carries its
confidence as a percentage, a badge when it exceeds the strong threshold, and
the translated list of reasons that produced it. Showing the reasons is a
deliberate product decision: a bare percentage invites either blind trust or
blind dismissal, whereas \dq{same category, same wilaya, photographs strongly
similar, found one day after the loss} lets the user apply judgement the system
does not have.

\subsection{Paid matching}
\label{sec:paid-matching}

Reporting, browsing, searching and claiming are free. What is paid is the
\emph{suggestion}: the identity of the report that the engine believes describes
the same object. Each account receives one free unlock; further unlocks cost one
credit each, and credits are sold in three packs (Table~\ref{tab:packs}).

Four implementation decisions carry this feature.

\begin{itemize}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{The redaction happens on the server.} A locked suggestion is
        stripped of the counterpart's title, photograph, place and date before
        it is serialised. Blurring in the browser would leave the answer one
        click away in the developer tools. What a locked card keeps is the
        confidence figure and a small blurred thumbnail generated at upload
        time --- the evidence that something real sits behind the lock.
  \item \textbf{Credits are a ledger, not a counter.} Every purchase, unlock and
        administrative grant is an append-only row; the balance is their sum.
        An unlock locks the user's row first and then checks, in order, whether
        the match is already unlocked, whether the free allowance remains, and
        whether the balance suffices --- so two simultaneous clicks cannot spend
        the same credit twice.
  \item \textbf{The payment gateway sits behind an interface.} Chargily
        Pay~\cite{chargily2026}, which accepts the national EDAHABIA and CIB
        cards, is reached through a \code{PaymentProvider} with two operations:
        create a checkout, and verify a webhook. The webhook's HMAC-SHA256
        signature is checked over the raw request bytes with a constant-time
        comparison, and credits are granted only from a verified webhook, never
        from the browser's return to the site. A simulated provider implements
        the same interface for development and demonstrations.
  \item \textbf{A confirmed match is never locked.} Once both parties have been
        told about a specific item, charging for the card that describes it
        would sell nothing but frustration.
\end{itemize}

Prices are whole dinars, the unit in which Chargily settles, and the fee is
absorbed by the platform so that the price shown is the price paid. The economic
consequences of this pricing are analysed in Chapter~\ref{ch:finance}.

\subsection{The claim workflow}

A match is a hypothesis, not an authorisation, so even an unlocked suggestion
never reveals anyone's contact details. Recovery goes through a separate claim:

\begin{enumerate}[leftmargin=1.6em,itemsep=3pt]
  \item The reporter sets up to two verification questions when publishing
        (\dq{Which side is scratched?}, \dq{What is the lock-screen
        photograph?}).
  \item A user who believes the item is theirs submits a claim answering those
        questions, with an optional message. The questions are snapshotted onto
        the claim, so the answers stay meaningful even if the reporter later
        edits them.
  \item The reporter reviews and approves or rejects.
  \item \textbf{Contact details are exchanged only on approval}, and only
        between those two people.
\end{enumerate}

One symmetric mechanism covers both directions: on a found item the loser proves
ownership, and on a lost item the finder proves possession. A partial unique
index permits only one \emph{pending} claim per person per item, which stops a
claimant from flooding a reporter while still allowing a fresh attempt after a
rejection.

\screenshot{claim.png}{Submitting a claim by answering the reporter's verification questions}{claim}

\subsection{Notifications and personal dashboard}

Notifications are created in-app when a match crosses the notification
threshold, when a claim is submitted, and when a claim is resolved. Each carries
a deep link to the item or match that caused it. The dashboard collects the
user's own reports with their live state --- the processing status while
embedding is in progress, the number of suggestions, and any claims awaiting
their decision.

\subsection{Administration console}

A platform that matches strangers and takes payments needs people who can
intervene. The administration console, reachable only by accounts with the
\code{admin} role, covers five areas: an overview of the platform's state
(accounts, open reports, recoveries, the rate at which owners confirm
suggestions, revenue, and the AI processing queue); accounts, which can be
suspended, reactivated, verified, promoted, or granted free unlocks; reports,
which can be taken down with a stated reason, restored, re-processed, or
stripped of an individual photograph; suggestions, which can be retracted from
both owners; and payments.

Every one of these actions writes a row to \code{admin\_actions} \emph{in the
same database transaction} as the change it records, so the audit log cannot
disagree with the data: either both are committed or neither is. Actions that
affect another person --- a suspension, a takedown --- require a reason. A
moderator's takedown is recorded with its own close reason, \code{removed},
distinct from a reporter withdrawing their own report, so that the two never
blur together in statistics. The first administrator can only be created from
the server's command line, which keeps the web interface free of any path to
privilege.

\screenshot{admin-overview.png}{Administration console, overview page, on the evaluation corpus}{admin}

\subsection{Trilingual interface and right-to-left support}

Every route is prefixed by a locale segment, and English, French and Arabic each
have a complete message catalogue of 905 keys. Arabic is rendered right-to-left;
because the styling uses logical rather than physical properties, the layout
mirrors without a parallel stylesheet. Localisation reaches further than the
interface strings: wilayas are stored as numeric codes and rendered per locale,
match explanations travel from the worker as reason codes and are translated on
the client, and the text encoder itself is multilingual, which is what allows a
description written in Arabic to match one written in French
(Section~\ref{sec:eval-crosslingual}).

\section{Testing and validation}

Testing is concentrated where a defect would be either invisible or expensive.
The backend suite holds 136 automated tests, all passing.

\begin{itemize}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{Scoring is pure and unit-tested.} Fusion, calibration,
        confidence and the margin rule are plain functions over plain values ---
        no database session, no model, no PyTorch --- so the entire scoring
        policy is tested in milliseconds without loading any weights.
  \item \textbf{Integration tests exercise the real HTTP surface} for
        authentication, the item lifecycle, billing and the administration
        endpoints, through the same validation and authorisation dependencies
        that run in production.
  \item \textbf{Security tests} cover token issuance, expiry, rotation, the
        reuse-detection path including its grace window, webhook signature
        checks, and the refusal to start with a weak signing secret.
  \item \textbf{Health endpoints} separate liveness from readiness: readiness
        checks the database and, when configured, Redis.
\end{itemize}

\subsection{Cross-lingual text retrieval}
\label{sec:eval-crosslingual}

\paragraph{Protocol.} Twelve everyday objects were each described three times,
as real posts would be: in English as a \emph{loss} report, and in French and
Arabic as \emph{found} reports, in different words --- for example \dq{Lost my
black Samsung Galaxy A54 at the bus station, the screen protector is cracked}
against \dq{Trouvé un téléphone Samsung noir à la gare routière, protection
d'écran fissurée}. A correct match must therefore survive both a change of
language and a rephrasing. For every ordered pair of languages, each of the 12
descriptions was used as a query against the 12 descriptions in the other
language, giving $6 \times 12 = 72$ queries per model. A query succeeds when its
nearest neighbour is the same object; the mean reciprocal rank (MRR) also
credits a correct answer found in second or third place.

\paragraph{Result.} The production model retrieved the right object first for
all 72 queries, with a wide gap between the mean similarity of descriptions of
the same object ($0.740$) and of different objects ($0.234$). The English-only
model manages between French and English, which share vocabulary and script,
but is no better than chance for Arabic: it found 4 of the 48 queries that
involve Arabic, where chance alone would find 4 (one in twelve). This is the
measured justification for the model choice of Section~\ref{sec:ml-stack}: with
an English-only encoder, an Arabic report would be invisible to the matching
engine. The set is small and hand-written, so the experiment establishes the
\emph{difference} between the two models rather than an accuracy figure for the
field.

\subsection{Limits of the evaluation}

The measurements above are honest but narrow, and four limits should be stated
plainly.

\begin{itemize}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{The corpus is small and built by the team.} Fifty-six reports
        cannot estimate precision or recall in the field, and reports written
        to exercise the system are cleaner than the public's.
  \item \textbf{No Arabic report exists in the corpus.} The cross-lingual
        capability is established by the controlled experiment of
        Section~\ref{sec:eval-crosslingual}, not by live data.
  \item \textbf{Notifications are written in English.} Match explanations are
        translated on the client, but the title and body of a notification are
        still generated in English by the worker; storing them as codes, like
        the explanations, is the planned fix.
  \item \textbf{No real payment has been processed.} The purchase flow was
        exercised end to end with the simulated provider. The Chargily adapter
        is written against the gateway's documented v2 interface and covered by
        tests of its signature check, but it has not yet exchanged a payment
        with Chargily: that requires a merchant account, which in turn requires
        the registered activity described in Chapter~\ref{ch:finance}.
\end{itemize}

The measurement that matters most --- how many objects are returned to their
owners --- can only come from a pilot with real users, and the system records
everything that pilot will need: suggestions, owner verdicts, claims and
recoveries.

\section{Deployment and packaging}

\paragraph{Development.} The whole system runs from a single
\code{docker compose up}. Five services are defined --- \code{postgres} (with
\code{pgvector}), \code{redis}, \code{api}, \code{worker} and \code{frontend}
--- with named volumes for database files, Redis persistence, uploaded media,
and the model cache. Caching the model weights in a volume matters more than it
appears to: without it, every container rebuild re-downloads several hundred
megabytes of weights before the worker can start. The API and the worker are
built from the same Dockerfile but install different dependency sets: the API
never imports PyTorch, and PyTorch is installed from the CPU wheel index,
because the default distribution bundles NVIDIA libraries this deployment
cannot use.

\paragraph{Production.} A separate deployment kit (\code{deploy/}) turns the
same images into a public service on any Linux virtual machine. It adds a Caddy
reverse proxy that obtains and renews HTTPS certificates automatically, keeps
PostgreSQL and Redis off the public network, restarts every service after a
failure or a reboot, rotates logs, and runs the platform in a \emph{staging}
mode in which payments use the simulated provider until a merchant account
exists. When no domain name has been bought, the server's address is turned
into a working hostname through a wildcard DNS service such as
\code{sslip.io}, so a certificate can still be issued. Two scripts move the
demonstration data across: one exports the database and the photographs from
the development machine, the other restores them on the server.

\paragraph{Rehearsal.} The production configuration was rehearsed end to end on
the development machine: the data import reproduced identical row counts, and a
cross-check report submitted through HTTPS was embedded and matched to its
counterpart at 94\,\% confidence. Because the free server targeted for the
demonstration uses ARM processors (Chapter~\ref{ch:finance}), the worker image
was also built for ARM64; this required pinning a different PyTorch build per
architecture, since the CPU-only wheel index serves x86 only.

\section{Conclusion}

This chapter has described the prototype as it stands and measured it: a
modular-monolith backend with all inference isolated on a background worker, a
PostgreSQL database doing relational filtering, full-text search and vector
similarity in one engine, a trilingual Next.js interface covering the full cycle
from report to recovery, a paid matching tier built on an auditable credit
ledger, and an administration console whose every action is recorded.

The measurements support the two central technical choices. The multilingual
encoder matched every one of 72 cross-language queries where an English-only
model failed almost all of those involving Arabic; and the calibration of the
image channel, motivated by the measured distribution of CLIP similarities,
keeps the typical unrelated photograph from counting as evidence. They also put
a number on what the platform costs to run: about 1.2\,GB of memory and no GPU,
which is the starting point of the financial plan that follows. What they cannot
show --- recovery rates with real users --- is the purpose of the pilot.
